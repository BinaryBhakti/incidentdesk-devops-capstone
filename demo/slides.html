1 · Project overview

  • IncidentDesk: an incident-management SaaS. Open incidents (service, SEV1–SEV4), move them OPEN → INVESTIGATING → RESOLVED, and watch live KPIs
  • Responsive React dashboard: KPI cards, filters, incident table, create modal
  • FastAPI REST API with 9 endpoints, plus /health, /ready and /metrics
  • PostgreSQL schema owned by Alembic migrations
  • Goal: show how one commit travels Git → CI → security gate → registry → Terraform → Kubernetes → monitoring, and how to troubleshoot it when it breaks

4 · CI/CD pipeline (GitHub Actions)

push to main
  ├─ Test ............ ruff · pytest -v (real Postgres service) · npm ci && vite build
  ├─ Secret scan ..... gitleaks over the full history
  ├─ Build/scan/push . docker build ×2 → Trivy (HIGH/CRITICAL, exit 1) → GHCR :<commit sha>
  ├─ Terraform ....... fmt · init · validate · plan (VPC+EKS) · apply · destroy (LocalStack)
  └─ Deploy .......... kind → Ingress → Prometheus/Grafana → helm upgrade --install
                       → smoke test via Ingress → load test → HPA → PromQL checks
                       → screenshots → Argo CD sync → troubleshooting lab
  • Each stage is a gate: a failing test or a fixable HIGH CVE means no image is pushed
  • Image tag = commit SHA, so production traces back to one exact commit

6 · Infrastructure as Code: Terraform

  • VPC 10.20.0.0/16 in ap-south-1
  • 2 public + 2 private subnets across 2 AZs, IGW, NAT, route tables
  • EKS cluster + managed node group (2 × t3.medium, private subnets)
  • IAM roles, security groups, S3 backups bucket, DynamoDB lock table
terraform init
terraform plan   # VPC + EKS
terraform apply
aws eks update-kubeconfig \
  --name incidentdesk-dev-eks
terraform destroy

No AWS account: CI runs it on LocalStack. The plan includes EKS; apply/destroy create and remove the network, IAM and storage (EKS is LocalStack Pro-only).

8 · Observability

  • /metrics: request count and latency histogram per route, plus incidents_created_total
  • Prometheus scrapes annotated pods and kube-state-metrics; 6 alert rules (backend down, not ready, restarts, error rate, p95 latency, HPA at max)
  • Grafana dashboard provisioned from code: pods up, req/s, error ratio, p50/p95/p99, CPU and memory per pod, HPA replicas
  • Answers: is traffic arriving? which endpoint is slow? are errors rising? is the HPA scaling?

10 · Key learnings

  • Gates belong before the registry: tests and the scanner decide what is allowed to exist
  • Liveness ≠ readiness: /ready checks the database, so traffic only reaches pods that can serve
  • SHA tags beat latest: rollback means picking a commit
  • A Service is only labels. Most "network" bugs are selector bugs
  • HPA needs requests and a metrics provider; Ingress needs a controller
  • Declare everything (Terraform, Helm, dashboards) so a rebuild looks identical
  • Be honest about limits: LocalStack and kind stand in for AWS and EKS here
